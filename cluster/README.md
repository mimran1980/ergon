# ergo-aeron-cluster

> **Hobby experiment — do not use in production.** This crate is an incomplete
> Rust exploration of an Aeron Cluster client. It has not received the testing,
> operational use, compatibility guarantees, or failure-mode validation required
> for production systems.

The crate combines rusteron's Aeron transport with Aeron Cluster protocol codecs
generated by ErgoSBE. It exists primarily to learn Aeron Cluster and to exercise
ErgoSBE against a real protocol.

The preferred long-term solution is for Aeron to release official Cluster C
client bindings and for rusteron to expose them. This hobby crate should not be
treated as a replacement for such support.

## Current scope

The current prototype explores:

- synchronous and asynchronous connection state;
- ingress publication and zero-copy claims;
- egress fragment assembly and controlled polling;
- session events, leader changes, keep-alives, and close requests;
- Aeron Cluster SBE schema generation through ErgoSBE;
- optional Java-backed integration and failover tests.

The implementation is not release ready. Known gaps include incomplete error
propagation, non-atomic leader reconnect state, allocation in high-level offer,
public internal codec surface, lossy text handling, and application-specific
RFQ/auction material that still needs removal. The corrected work is tracked in
the repository's single [`implementation plan`](../docs/IMPLEMENTATION_PLAN.md).

## Build and test

Pure Rust checks:

```sh
cargo test -p ergo-aeron-cluster --lib
cargo clippy -p ergo-aeron-cluster --all-targets -- -D warnings
cargo doc -p ergo-aeron-cluster --no-deps
cargo bench -p ergo-aeron-cluster --no-run
```

Some integration tests and current examples use the optional Java harness. They
require Java 17+, Aeron jars, and a suitable local Aeron environment:

```sh
just build-aeron-jars
just test-aeron-cluster-harness
```

These tests do not make the crate production ready.

## Intended high-level interface

Application code should use the high-level `AeronCluster` client and typed
`Result` methods. `offer_raw` represents transport status and is not the example
interface; normal examples should use `offer`, while latency-sensitive callers
can use `try_claim` explicitly.

Cluster protocol fields retain their real semantics:

- session-event detail and ingress endpoints are schema-declared ASCII text and
  should be exposed as borrowed `&str` by high-level views;
- credentials, challenges, principals, application messages, and nested SBE
  payloads remain borrowed byte slices;
- malformed text or protocol frames are errors, never placeholder strings.

Generated protocol codecs are an implementation detail. The planned published
surface will expose only deliberate client configuration, lifecycle, polling,
event, error, offer, and claim types.

## Examples

The release target is three small examples:

1. connect and echo;
2. controlled polling;
3. leader failover.

Current RFQ and auction examples are historical application experiments and must
not be copied as recommended usage. They are scheduled for deletion rather than
promotion into the generic client.

## Non-goals

- Production safety, support, or compatibility guarantees.
- A Rust Cluster service implementation.
- Replacing official Aeron Cluster client bindings.
- Generic topic routing, commit tracking, RFQ, auction, or order-workflow APIs.
- Hiding Aeron back pressure or administrative actions behind an infallible
  interface.

## Publication

`ergo-aeron-cluster` may eventually be published as a clearly labelled `0.x`
hobby prototype. Publication is blocked until the Cluster tasks and release
acceptance commands in the implementation plan pass and the package excludes
the Java harness, reference codecs, tests, and application protocols.
